# SRE Agent 지식 문서 디자인 가이드

> **목적**: SRE Agent가 인시던트 조사 시 **검색해서 인용하기 좋은** 지식 문서를 일관된 품질로 작성·운영하기 위한 규칙.

## 0. 핵심 원칙 (3줄 요약)
1. **문서 1개 = 장애유형 1개** — 잘게 쪼갤수록 RAG 검색 정확도가 올라간다.
2. **증상 키워드를 앞·제목·frontmatter에** — 알림 제목과 매칭되는 단어를 노출한다.
3. **도구는 사실, 문서는 해석** — 판정 기준·조치·runbook을 문서가 담고, 측정은 진단도구가 한다.

## 1. 파일·폴더 규칙
| 항목 | 규칙 | 예 |
|------|------|-----|
| 파일명 | `KB-<대상>-<주제>.md` (영문, 하이픈) | `KB-EventHub-Consumer-Lag.md` |
| 폴더 | 제품/도메인별 분리 가능 | `Knowledge/EventHub/`, `Knowledge/Windows/` |
| 인코딩 | UTF-8 | — |
| 언어 | 한국어 본문 + 영문 키워드 병기 | "소비 지연(consumer lag)" |

## 2. 프론트매터(YAML) 스키마
문서 최상단에 메타데이터를 넣어 검색·라우팅 정확도를 높인다.

```yaml
---
title: "사람이 읽는 제목"
keywords: [증상어, 동의어, 영문키워드, 리소스명]   # RAG 매칭 핵심
resource_types: [Microsoft.EventHub/namespaces]     # 어떤 리소스에 적용?
severity_hint: [warning, critical]                   # 예상 심각도
mcp_tool: diagnose_eventhub                          # 연계 진단도구(있으면)
data_source: [Azure Monitor, Log Analytics]          # 데이터 출처
version: 1.0.0
last_updated: 2026-07-22
---
```
- `keywords`는 **알림 제목/메트릭명/동의어**를 최대한 담는다(한·영 병기). 이게 검색 적중률을 좌우한다.
- `mcp_tool`은 문서와 도구를 연결해 Agent가 "이 증상 → 이 도구 실행"을 추론하게 한다.

## 3. 표준 섹션 구조 (필수 골격)
모든 KB는 아래 8개 섹션을 유지한다. (증상/원인/진단/판정/조치/검증/롤백/연계)

| # | 섹션 | 내용 | 목적 |
|---|------|------|------|
| 1 | **증상(Symptoms)** | 관찰되는 현상 + 알림 제목 예시 | 검색·매칭 진입점 |
| 2 | **원인 후보(Causes)** | 원인 + 각 원인의 식별 신호(표) | 가설 좁히기 |
| 3 | **진단(Diagnosis)** | 진단도구 호출 예 + 수동 명령(PowerShell/KQL) | 사실 수집 |
| 4 | **판정 기준(Thresholds)** | 양호/주의/위험 임계값(표) | 심각도 판단·`knowledge_context` 주입원 |
| 5 | **조치(Remediation)** | 원인별 단계적 조치 | 실행 가능한 권장 |
| 6 | **검증(Verification)** | 조치 후 확인 방법·기준 | 재발 방지 확인 |
| 7 | **롤백/주의(Rollback & Caveats)** | 되돌리기·부작용·비가역 작업 경고 | 안전 |
| 8 | **참고/연계(References)** | 관련 도구·문서·자율 발견 루프 | 확장 |

## 4. 작성 스타일
- **판정 기준은 반드시 표(table)로** → Agent가 값을 추출해 도구 파라미터로 주입하기 쉽다.
- 조치는 **"원인 → 조치" 번호 목록**으로, 명령·파라미터를 구체적으로.
- 코드블록에는 **실행 가능한 실제 명령**(PowerShell/KQL/MCP 호출)을 넣는다.
- 되돌릴 수 없는 작업(파티션 증설, 재배포, 파일시스템 변경)은 **롤백 섹션에 명시적 경고**.
- 한 문서가 너무 길면(> 2~3 스크롤) 하위 유형으로 분할.

## 5. 진단도구와의 연결 (일관성 규칙)
- 문서의 판정 기준·조치 문구는 진단도구 출력(`health_score`, `recommended_actions`)과 **용어·임계값을 일치**시킨다.
- 고객 고유 임계값은 문서 표 → Agent가 읽어 도구에 `knowledge_context`(방법 A)로 주입 → 보고서에 반영.
- `needs_input` 자율 발견 루프가 있는 도구(eh checkpoint_store 등)는 **"어디서 찾는지"를 문서 참고 섹션에 기술**.

## 6. 버전·리뷰 운영
- 문서 상단 `version`/`last_updated` 유지, 변경 시 갱신.
- **포스트모템 루프**: 실제 해결된 인시던트의 근본원인·최종조치를 해당 KB에 다시 반영(핵심!).
- 임계값·조치가 틀린 것으로 판명되면 **즉시 수정 또는 폐기**(잘못된 지식은 오답을 유발).
- 분기별로 keyword 적중률·미사용 문서 점검.

## 7. Do / Don't
| Do | Don't |
|----|-------|
| 장애유형 1개당 문서 1개 | 여러 장애를 한 문서에 몰아넣기 |
| 증상 키워드 다수 노출 | 제목만 있고 본문에 검색어 부족 |
| 실행 가능한 명령 삽입 | 추상적 서술만 |
| 임계값을 표로 | 문장 속에 숨긴 수치 |
| 롤백/부작용 경고 | 비가역 작업을 조치에만 나열 |
| 도구 출력과 용어 일치 | 도구와 다른 임계값·명칭 사용 |

## 8. 최소 체크리스트 (문서 발행 전)
- [ ] 프론트매터에 keywords(한·영), resource_types, severity_hint 있음
- [ ] 8개 표준 섹션 모두 존재
- [ ] 판정 기준이 표로 정리됨
- [ ] 진단도구 호출/수동 명령이 실행 가능
- [ ] 비가역 작업에 롤백·경고 명시
- [ ] 관련 진단도구(`mcp_tool`)와 용어 일치
